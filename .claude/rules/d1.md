# D1

`akademia-rejestracje`, created with `--jurisdiction eu` — fixed at creation,
cannot be changed. It holds physicians' names, PWZ numbers, phones and invoice
data, so treat every query as touching personal data.

## Migrations

Not part of any deploy workflow. Apply by hand, before the deploy that needs
them, and only in a direction the running code tolerates:

```bash
npx wrangler d1 migrations apply akademia-rejestracje --remote
```

An applied migration is immutable — add a new file, never edit an old one.
SQLite cannot alter a `CHECK` constraint, so widening one means rebuilding the
table with explicit column lists (see `0002_manual_source.sql`).

## Limits to design against

| | |
| --- | --- |
| Bound parameters per query | **100** — never build `IN (?,?,…)` from an unbounded list |
| SQL statement length | 100 KB |
| Query duration | 30 s |
| Row / string / BLOB | 2 MB |
| Columns per table | 100 |
| Database size | 10 GB (Paid) |
| Time Travel | 30 days (Paid) — the only backup besides the admin CSV export |

No interactive transactions: `BEGIN`/`COMMIT` are unavailable and D1
auto-commits. `db.batch()` is the transaction primitive — one implicit
transaction, executed sequentially, rolled back as a whole if a statement fails.

## Model invariants

- **Capacity is never stored.** The limit comes from the CMS; seats taken are
  `COUNT(*) WHERE status='confirmed'`. Pending rows hold no seat — that is the
  point of the review step. Nothing is written back to git.
- `price_amount` is a snapshot taken at registration time. Never re-derive it
  from the current course data; that was the Google Form's bug.
- `course_slug` + `date_start` reference MDX, not a table — there is no FK, so
  validate against `/terminy.json` before writing.
- Keep queries served by `idx_reg_slot (course_slug, date_start, status)` or
  `idx_reg_created (created_at DESC)`.
